🆕 Novedades del backend

🔐 Seguridad JWT + roles

  • Todas las rutas privadas exigen Bearer token.
  • Las escrituras se restringen con roles_required.
  • La cuenta y el rol se verifican contra la base en cada request.
  • Al deshabilitar un usuario, su token queda revocado al instante.

👨‍🏫 Alta de profesores con aprobación

  • El profesor se registra solo con POST /api/auth/register-profesor.
  • La cuenta se crea inactiva y sin centros.
  • El ADMIN la habilita con PUT /api/profesores/:id.
  • La habilitación sincroniza persona, usuario y profesor.

⚙️ Rol y estado configurables

  • POST /api/profesores acepta rol (PROFESOR/ADMIN).
  • También acepta activo booleano.
  • Valores inválidos devuelven 400.
  • El auto-registro público ignora esos campos (anti-escalada).

🧪 Validaciones y consistencia

  • Contraseñas de mínimo 8 caracteres.
  • DNI y email únicos a nivel global (409, no 500).
  • Un PUT sin cambios devuelve 200 si el registro existe.
  • Usuario y email duplicados devuelven 409.

💬 Chat y pagos

  • El emisor del chat se toma del token, no del body.
  • Solo el autor o un ADMIN pueden borrar un mensaje.
  • Pagos pendientes para PROFESOR/ADMIN.
  • Confirmar o rechazar un pago es solo ADMIN.

🔧 Correcciones técnicas

  • requirements.txt completo y load_dotenv() al inicio.
  • Corrección de DB_PASS / DB_PASSWORD.
  • Decoradores HTTP eliminados del repositorio (evitaba 500).
  • Limpieza de __pycache__ y .gitignore ampliado.

🔄 Flujo completo de alta de un profesor

  1. El profesor completa POST /api/auth/register-profesor (público) y recibe 201.
  2. La cuenta queda con rol PROFESOR, activo = false en las tres tablas y sin centros.
  3. Si intenta loguearse, recibe 403: "pendiente de habilitación por un administrador".
  4. El ADMIN consulta GET /api/profesores?todos=true y detecta los pendientes.
  5. El ADMIN envía PUT /api/profesores/:id con activo: true y los centro_ids.
  6. El profesor ya puede iniciar sesión y usar la API con su token PROFESOR.
  7. Si el ADMIN lo vuelve a deshabilitar, el acceso se corta de inmediato.

Reglas de seguridad

Token verificado contra la BD en cada request: si el usuario o la persona se deshabilitan, su token deja de funcionar inmediatamente (403). El rol también se refresca desde la base, no se confía en el rol viejo del JWT.
Contraseñas: mínimo 8 caracteres en POST /api/auth/register, POST /api/auth/register-profesor, POST /api/alumnos, POST /api/profesores y PUT /api/perfil/password.
Anti-escalada de privilegios: /api/auth/register siempre crea ALUMNO y /api/auth/register-profesor siempre crea PROFESOR inactivo. Los campos rol, activo y centro_ids enviados a esos endpoints públicos se ignoran. Solo un ADMIN puede asignar el rol ADMIN.
Integridad: DNI y email son únicos a nivel global de persona; usuario es único en usuario. Los duplicados devuelven 409, no 500.
